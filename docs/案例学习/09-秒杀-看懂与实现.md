# 案例9 · 秒杀库存扣减（Redisson 分布式锁）

> 技术方案：Redis DECR 预扣 + Redisson 分布式锁保护数据库
> 学什么：**分布式锁**（面试最高频，必须吃透）
>
> 这是全部案例里最难的一个，但拆开看就 4 步。

---

# Part A · 看懂版

## A1. 全景流程图（秒杀一个商品的完整 4 阶段）

```
POST /api/stock/3/seckill?userId=1
   │
   ▼
StockService.seckill(3, 1)
   │
   ├─ 阶段1 Redis 预扣库存（不加锁，DECR 天然原子）
   │     decrement(stockKey)          = DECR stock:product:3
   │     （remain < 0 → 回补 +1，返回失败"库存不足"）
   │
   ├─ 阶段2 获取分布式锁
   │     lock.tryLock(3, 30, SECONDS)（最多等 3 秒，锁 30 秒，看门狗续期）
   │     （拿不到锁 → 回补库存，返回"系统繁忙"）
   │
   ├─ 阶段3 数据库扣库存（临界区）
   │     productRepository.deductStock(3)  = UPDATE ... SET stock=stock-1 WHERE id=3 AND stock>0
   │     （affected == 0 → 回补，返回失败）
   │
   └─ 阶段4 finally 释放锁
         if (locked && lock.isHeldByCurrentThread()) lock.unlock();
```

## A2. 核心：为什么用 Redisson，而不是手写 SETNX？（面试必答）

手写分布式锁要自己处理 3 个经典难题，Redisson 全帮你解决了：

| 难题 | 手写要踩的坑 | Redisson 怎么解决 |
|------|-------------|------------------|
| 锁过期时间设多长？ | 业务没跑完锁就过期了 | **看门狗**默认每 10 秒自动续期到 30 秒 |
| 释放锁怎么防误删？ | A 的锁被 B 释放 | unlock 用 **Lua 脚本校验持有者**，不是自己的锁删不掉 |
| 拿不到锁怎么办？ | 忙等或放弃 | `tryLock(wait, lease, unit)` 支持**等待重试** |

**一句话**：Redisson 的 `getLock()` 基于 Lua 脚本实现「加锁+过期+可重入」原子性，看门狗续期 + 释放校验持有者，是生产级分布式锁。

## A3. 逐行翻译

```java
// 阶段1：Redis 预扣（不加锁，DECR 原子，性能高）
Long remain = stringRedisTemplate.opsForValue().decrement(stockKey);  // DECR
if (remain == null || remain < 0) {
    stringRedisTemplate.opsForValue().increment(stockKey);  // INCR 回补（把 -1 加回来）
    return false;
}

// 阶段2：拿分布式锁
RLock lock = redissonClient.getLock(lockKey);
locked = lock.tryLock(3, 30, TimeUnit.SECONDS);   // 等 3 秒、锁 30 秒

// 阶段3：数据库原子扣减（临界区，被锁保护）
int affected = productRepository.deductStock(productId);  // UPDATE ... WHERE stock > 0

// 阶段4：finally 释放
if (locked && lock.isHeldByCurrentThread()) {
    lock.unlock();
}
```

## A4. 为什么「DECR 预扣」之后，数据库扣减还要加锁？

- Redis 的 `DECR` 能保证「Redis 里的库存」原子，但最终要**落库（MySQL）**；
- 数据库扣减 + 记订单等操作必须**串行化**，否则并发下数据库也超卖；
- 所以：Redis 预扣挡掉大部分无效请求（快），锁保护数据库临界区（稳），**双重保证**。

## A5. 测试剧本（并发验证不超卖）

```java
initStock(3, 5)                 // 初始化 5 件
100 个并发 seckill(3, uid)       // 并发抢
assertTrue(successCount <= 5)   // 成功数 ≤ 5（不超卖）
assertEquals(0, getStock(3))    // 库存归 0，不为负数
```

## A6. 记忆锚点

- `decrement`=DECR 预扣、`increment`=INCR 回补。
- Redisson：`getLock` → `tryLock(wait, lease, unit)` → `isHeldByCurrentThread` → `unlock`。
- **看门狗**：默认每 10 秒续期到 30 秒，防止业务没跑完锁过期。

# Part B · 从0实现版

## B1. 需求

> 秒杀扣库存，并发下不能超卖（库存不能变负数）。

## B2. 内心独白

> 单机可以用 synchronized，但分布式环境多台服务器，synchronized 管不住。
> 用 Redis 做分布式锁：先用 DECR 快速预扣（挡掉库存不足的），再拿锁串行化数据库扣减（保证不超卖），最后 finally 释放。

## B3. 手写代码（只写核心 Service）

```java
@Service
@RequiredArgsConstructor
public class StockService {

    private final RedissonClient redissonClient;
    private final StringRedisTemplate redis;
    private final ProductMapper productMapper;

    public boolean seckill(Long productId, Long userId) {
        String stockKey = "stock:product:" + productId;
        String lockKey = "lock:stock:deduct:" + productId;

        // 阶段1：Redis 预扣（原子，不加锁）
        Long remain = redis.opsForValue().decrement(stockKey);   // DECR
        if (remain == null || remain < 0) {
            redis.opsForValue().increment(stockKey);             // 回补 INCR
            return false;
        }

        // 阶段2：拿分布式锁
        RLock lock = redissonClient.getLock(lockKey);
        boolean locked = false;
        try {
            locked = lock.tryLock(3, 30, TimeUnit.SECONDS);
            if (!locked) {
                redis.opsForValue().increment(stockKey);         // 回补
                throw new RuntimeException("系统繁忙");
            }

            // 阶段3：数据库原子扣减（临界区）
            int affected = productMapper.deductStock(productId); // UPDATE ... WHERE stock > 0
            if (affected == 0) {
                redis.opsForValue().increment(stockKey);         // 回补
                return false;
            }
            return true;
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            redis.opsForValue().increment(stockKey);
            return false;
        } finally {
            // 阶段4：释放锁（判断持有者，防误删）
            if (locked && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

## B4. 与前面案例的区别（记住这一句）

> 前面都是「存/取数据」，案例9 用 Redis 做**并发控制**（分布式锁）。Redis 除了缓存，还能解决分布式下的互斥问题。

## B5. 自测标准

> 能画出「DECR 预扣 → tryLock → 数据库扣减 → finally unlock」四步流程，并能说出看门狗作用（自动续期防锁过期），案例9 就掌握了。这是面试最高频的一题，务必吃透。
