# 案例10 · 消息通知（Pub/Sub 发布订阅）

> 技术方案：Redis Pub/Sub 一对多广播
> 学什么：**发布/订阅模型**（了解即可，生产用 MQ）
>
> 脚手架见《00-总纲》，本文只讲增量。

---

# Part A · 看懂版

## A1. 全景流程图（三个文件各司其职）

```
NoticePublisher.publish("订单已发货")
   │  convertAndSend(channel, message)
   ▼
Redis PUBLISH channel:notice "订单已发货"
   │
   ▼
（所有订阅了 channel:notice 的订阅者实时收到）
   ▼
NoticeSubscriber.onMessage(...)   ← 回调，打印/处理
```

**关键：发布者不关心谁在听，订阅者按频道接收，天然解耦。** 这跟前面 9 个案例"主动读写"完全不同——它是**被推送**。

## A2. 三个文件各干什么

| 文件 | 角色 | 核心代码 |
|------|------|---------|
| `NoticePublisher` | 发布者 | `convertAndSend` |
| `NoticeSubscriber` | 订阅者 | `implements MessageListener` → `onMessage` |
| `RedisPubSubConfig` | 接线 | 把订阅者注册到容器 + 订阅频道 |

## A3. 逐行翻译

```java
// 发布者（一行）
Long receivers = stringRedisTemplate.convertAndSend(CHANNEL_NOTICE, message);
// = PUBLISH channel:notice "订单已发货"；返回"收到消息的订阅者数量"

// 订阅者（回调）
public class NoticeSubscriber implements MessageListener {
    public void onMessage(Message message, byte[] pattern) {
        String channel = new String(message.getChannel(), UTF_8);  // 频道名
        String body = new String(message.getBody(), UTF_8);        // 消息内容
        // TODO 业务处理：推送、发短信、更新状态...
    }
}

// 配置（接线）
container.addMessageListener(
    new MessageListenerAdapter(noticeSubscriber),     // 监听器
    new ChannelTopic(CHANNEL_NOTICE));                // 订阅哪个频道
```

## A4. 缺点（面试重点，务必记住）

> **Pub/Sub 消息不持久化**：订阅者不在线就收不到，消息会丢。
> 需要可靠消息（不丢、可重试）时用 **Stream / RabbitMQ / Kafka**。

## A5. 测试剧本

```java
publish("订单已发货");   // 发布
Thread.sleep(500);      // 等异步回调
// 观察控制台：【收到通知】频道=channel:notice, 内容=订单已发货
```

## A6. 记忆锚点

- 发布：`convertAndSend` = `PUBLISH`；订阅：`implements MessageListener` → `onMessage`。
- **一对多广播 + 解耦**用 Pub/Sub；**要可靠不丢**用 MQ。

# Part B · 从0实现版

## B1. 需求

> 发布一条通知，所有订阅者实时收到。

## B2. 内心独白

> 这是一对多广播：发布者发一条，多人同时收。发布者不需要知道谁在听 → 用 Pub/Sub 解耦。
> 但要写 3 样东西：谁发（发布者）、谁收（订阅者）、怎么连起来（配置）。

## B3. 手写代码（3 个文件）

```java
// ① 发布者
@Service
@RequiredArgsConstructor
public class NoticePublisher {
    private final StringRedisTemplate redis;
    public void publish(String message) {
        redis.convertAndSend("channel:notice", message);   // PUBLISH
    }
}
```

```java
// ② 订阅者
@Slf4j
@Component
public class NoticeSubscriber implements MessageListener {
    @Override
    public void onMessage(Message message, byte[] pattern) {
        String channel = new String(message.getChannel(), StandardCharsets.UTF_8);
        String body = new String(message.getBody(), StandardCharsets.UTF_8);
        log.info("收到通知: channel={}, body={}", channel, body);
        // 业务处理写这里
    }
}
```

```java
// ③ 接线配置
@Configuration
@RequiredArgsConstructor
public class PubSubConfig {
    private final NoticeSubscriber subscriber;

    @Bean
    public RedisMessageListenerContainer container(RedisConnectionFactory factory) {
        RedisMessageListenerContainer c = new RedisMessageListenerContainer();
        c.setConnectionFactory(factory);
        c.addMessageListener(new MessageListenerAdapter(subscriber), new ChannelTopic("channel:notice"));
        return c;
    }
}
```

## B4. 与前面案例的区别（记住这一句）

> 前面都是「我去读/写 Redis」，案例10 是「**Redis 主动推给我**」。发布者和订阅者通过频道解耦，谁也不认识谁。

## B5. 自测标准

> 能说清「发布者 / 订阅者 / 接线配置」三者的关系，并能说出 Pub/Sub 的缺点（不持久化会丢消息），案例10 就掌握了（了解即可，优先级最低）。
