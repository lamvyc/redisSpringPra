# 案例7 · 接口限流（INCR + EXPIRE）

> 技术方案：固定窗口计数限流，INCR 原子自增 + 第一次 EXPIRE 定窗口
> 学什么：**Redis 做计数器**（这是和"缓存"完全不同的用法）
>
> 脚手架见《00-总纲》，本文只讲增量。

---

# Part A · 看懂版

## A1. 全景流程图

```
GET /api/rate-limit/test（连续请求）
   │
   ▼
RateLimitService.tryAcquire(ip)
   ├─ ① increment(key)               = INCR rate:limit:192.168.1.100   （计数 +1）
   ├─ ② 若 count == 1 → expire(key)  = EXPIRE ... 60                    （第一次才设窗口）
   └─ ③ 若 count > 10 → 抛 429       （超阈值，拒绝）
```

## A2. 核心：为什么限流用 Redis 计数，不用 MySQL？

限流是「高频 + 低价值」的计数操作，打 MySQL 压力巨大。Redis 单线程原子自增，10 万+ QPS。

## A3. 逐行翻译

```java
Long count = stringRedisTemplate.opsForValue().increment(key);   // INCR：原子自增，返回新值
// 第一次请求返回 1

if (count != null && count == 1) {
    stringRedisTemplate.expire(key, Duration.ofSeconds(windowSeconds));  // EXPIRE：定窗口 60 秒
}

if (count != null && count > maxRequests) {
    throw new BizException(429, "请求过于频繁");   // 超阈值 → 限流
}
```

## A4. ⭐ 最大的坑：为什么只在「第一次」设置 EXPIRE？

```java
if (count == 1) expire(...);   // ✅ 只在第一次设，窗口固定 60 秒
```

如果**每次都 EXPIRE**：
- 第 1 次请求设 60 秒；
- 第 2 次请求又重置 60 秒；
- … 只要一直有请求，窗口永远不到期 → **限流窗口"滑动"了，限流失效**。

**只在第一次设**，窗口就是「从第一次请求起算的固定 60 秒」，这是「固定窗口算法」的核心。

## A5. 测试剧本

```java
for (i = 0; i < 10; i++) tryAcquire(ip);   // 前 10 次正常（max-requests=10）
tryAcquire(ip);                            // 第 11 次抛异常（限流）
```

## A6. 记忆锚点

- `increment` = `INCR`（原子自增，第一次返回 1）。
- **固定窗口**：只在 `count == 1` 时设 EXPIRE，否则窗口滑动限流失效。

---

# Part B · 从0实现版

## B1. 需求

> 每个 IP 每分钟最多 10 次请求，超过返回 429。

## B2. 内心独白

> 这是「计数」不是「缓存」。要一个计数器，每次请求 +1，超过阈值就拒绝。用 Redis 的 INCR 原子自增（不用管并发）。窗口到期要清零 → 用 EXPIRE 让 key 自动删除。关键：只在第一次设过期，否则窗口永远不结束。

## B3. 手写代码

```java
@Service
@RequiredArgsConstructor
public class RateLimitService {

    private final StringRedisTemplate redis;

    public boolean tryAcquire(String ip) {
        String key = "rate:limit:" + ip;

        // INCR 原子自增
        Long count = redis.opsForValue().increment(key);

        // 第一次请求才定窗口（固定窗口，不能每次 EXPIRE）
        if (count != null && count == 1) {
            redis.expire(key, Duration.ofSeconds(60));
        }

        // 超阈值拒绝
        if (count != null && count > 10) {
            throw new RuntimeException("请求过于频繁");
        }
        return true;
    }
}
```

## B4. 与前面案例的区别（记住这一句）

> 前面是「缓存数据」，案例7 是「**计数**」。Redis 不仅能存数据，还能靠 `increment` 原子计数做限流、统计等。

## B5. 自测标准

> 能说出「为什么只在第一次 EXPIRE」（否则固定窗口变滑动窗口），并能默写 `increment` + `expire` 组合，案例7 就掌握了。
