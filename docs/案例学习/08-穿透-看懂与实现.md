# 案例8 · 缓存穿透防护（空对象 + 布隆过滤器思想）

> 技术方案：缓存空对象 + Set 模拟布隆过滤器
> 学什么：**缓存三大问题之一「穿透」的两种解法**（面试必考）
>
> 脚手架见《00-总纲》，本文只讲增量。

---

# Part A · 看懂版

## A1. 什么是缓存穿透？（先搞懂问题）

恶意请求大量访问**数据库中不存在的数据**（如 id=-1、随机 id）。缓存永远不命中 → 每次都打到数据库 → 数据库被打爆。

```
正常：请求 → 缓存命中/未命中 → 查库
穿透：请求(不存在的id) → 缓存永远不命中 → 每次都查库 → 数据库压力巨大
```

## A2. 解法一：缓存空对象

```java
// getProductWithProtection —— 查不存在的商品
Object cached = redisTemplate.opsForValue().get(key);   // GET
if (cached != null) {
    if (EMPTY_VALUE.equals(cached)) return null;   // 命中"空对象" → 直接返回 null，不再查库
    return (Product) cached;
}

Optional<Product> dbResult = productRepository.findById(productId);
if (dbResult.isEmpty()) {
    // 查不到也缓存一个"空标记"，短 TTL 3 分钟
    redisTemplate.opsForValue().set(key, EMPTY_VALUE, EMPTY_TTL);   // SET key "EMPTY" EX 180
    return null;
}
```

**核心思想**：查不到也缓存一个「空对象」（3 分钟短 TTL），后续相同请求直接命中空对象，不再打数据库。

**为什么空对象 TTL 要短（3 分钟）？** 万一这条数据稍后真的插入了，短 TTL 保证它很快能重新读到。

## A3. 解法二：布隆过滤器思想（用 Set 模拟）

```java
// getUserWithBloomFilter —— 查询前先过过滤器
Boolean maybeExists = redisTemplate.opsForSet().isMember(BLOOM_USER, String.valueOf(userId));  // SISMEMBER
if (!Boolean.TRUE.equals(maybeExists)) {
    throw new BizException("用户不存在（已被过滤器拦截）");   // 拦截，不查缓存不查库
}
// 存在才继续走「缓存 → 库」正常流程
```

**核心思想**：查之前先问"这个 id 是否可能存在"，不可能存在就直接拒绝，从源头拦截。

**为什么真实项目用布隆过滤器而不是 Set？** 数据量大（亿级）时 Set 太占内存；布隆过滤器用位数组+多次哈希，体积小 10 倍以上。本案例用 Set 只为演示「先过滤再查询」的思想。

## A4. 三大缓存问题速记（面试必背）

| 问题 | 场景 | 解法 |
|------|------|------|
| **穿透** | 查**不存在**的数据 | 空对象 + 布隆过滤器 |
| **击穿** | 热点 key 过期瞬间打库 | 互斥锁 + 逻辑过期 |
| **雪崩** | 大量 key 同时过期 | 过期时间加随机值 + 多级缓存 |

## A5. 测试剧本

```java
getProductWithProtection(999)  // 查不存在商品 → 返回 null + 写空对象
getProductWithProtection(999)  // 再查 → 命中空对象，不查库（仍 null）
getUserWithBloomFilter(999)    // 未注册 → 被过滤器拦截，抛异常
registerUserId(1)              // 注册到过滤器
getUserWithBloomFilter(1)      // 正常查询
```

## A6. 记忆锚点

- **穿透** = 查不存在的数据 → 空对象（短 TTL）+ 布隆（先过滤）。
- `isMember` = `SISMEMBER`（布隆思想用的就是案例3 的 Set 判断）。

# Part B · 从0实现版

## B1. 需求

> 防缓存穿透：查不存在的商品不打爆数据库。

## B2. 内心独白

> 问题是「不存在的 id 每次都查库」。两个办法：
> ① 查不到也缓存个空标记，下次命中空标记就不查库；
> ② 查之前先判断 id 是否可能存在，不可能就直接拒绝。
> 用①的「空对象」+ ②的「Set 模拟布隆」双保险。

## B3. 手写代码（只写增量）

```java
@Service
@RequiredArgsConstructor
public class CachePenetrationService {

    private final RedisTemplate<String, Object> redis;   // 存空对象
    private final StringRedisTemplate stringRedis;        // 存布隆 Set
    private final ProductMapper productMapper;

    private static final String EMPTY = "EMPTY";

    public Product getProduct(Long id) {
        String key = "product:detail:" + id;

        Object cached = redis.opsForValue().get(key);   // GET
        if (cached != null) {
            if (EMPTY.equals(cached)) return null;      // 命中空对象，直接返回
            return (Product) cached;
        }

        Product p = productMapper.selectById(id);
        if (p == null) {
            // 查不到：缓存空对象，短 TTL 3 分钟
            redis.opsForValue().set(key, EMPTY, Duration.ofMinutes(3));  // SET ... EX 180
            return null;
        }

        redis.opsForValue().set(key, p, Duration.ofMinutes(30));
        return p;
    }

    public User getUserWithBloom(Long id) {
        // 先过滤：SISMEMBER bloom:user <id>
        Boolean exists = stringRedis.opsForSet().isMember("bloom:user", String.valueOf(id));
        if (!Boolean.TRUE.equals(exists)) {
            throw new RuntimeException("用户不存在（过滤器拦截）");
        }
        // 存在才查缓存/库...
    }
}
```

## B4. 与案例1 的区别（记住这一句）

> 案例1 是「查不到就抛异常」，案例8 是「查不到也**缓存空对象** + 查询前先**过滤**」，防的是「大量不存在的 id 把数据库打爆」。

## B5. 自测标准

> 能说出穿透/击穿/雪崩三者的区别和各自解法，并能默写「空对象缓存」那段 `if (EMPTY.equals(cached)) return null;`，案例8 就掌握了。
