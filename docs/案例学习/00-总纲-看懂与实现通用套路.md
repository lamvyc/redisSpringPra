## 一、三条铁律（先记住，否则每个案例都懵）

1. **RedisTemplate 是「遥控器」**：`opsForXxx()` 选数据结构，后面每个方法名就是 Redis 命令的驼峰翻译。
   `increment`→`INCR`、`isMember`→`SISMEMBER`、`getExpire`→`TTL`。
2. **Redis 只有 5 种结构**：String / Hash / List / Set / ZSet，对应 `opsForValue/opsForHash/opsForList/opsForSet/opsForZSet`。
3. **两个 Template 怎么选**：
   - `RedisTemplate<String, Object>` → 存**对象**（User/Product），value 自动 JSON 序列化；
   - `StringRedisTemplate` → 存**纯字符串/数字/集合成员**，redis-cli 里可读。
   > 完整 API↔命令对照见 `docs/Redis命令与JavaAPI破译表.md`。

## 二、「看懂」四问模板（读任何 Service 都套这 4 问）

拿到一个看不懂的 Service，只问 4 个问题：

| # | 问题 | 看哪里 |
|---|------|--------|
| 1 | 它 `opsForXxx()` 是哪一种结构？ | 决定了底层是 String/Hash/Set/ZSet 的哪一种 |
| 2 | 读写删了什么 key？ | 对照 `RedisKeyConstants`，key 名 = 业务含义 |
| 3 | TTL 设了多久、为什么？ | 过期时间 = 这个数据的「保鲜期」 |
| 4 | 类注释里「为什么用这个结构」？ | **本项目最值钱的一句话（选型理由）** |

看懂 = 回答得出这 4 问。答不出，就是还没看懂。

## 三、「从0实现」六步施工顺序（固定套路）

**核心原则：自底向上，一层搭完验证一层，再搭上一层。**

```
第 1 步：说清需求     （一句话：输入什么、输出什么、数据放哪）
第 2 步：建表 + 实体   （数据长什么样）
第 3 步：写 Mapper     （怎么从 MySQL 拿数据）
第 4 步：写 Service     （业务逻辑，Redis 和 MySQL 在这里"串"起来）★ 最难，重点
第 5 步：写 Controller  （暴露 HTTP 接口）
第 6 步：启动 + 分层验证（先查库通不通，再查缓存通不通）
```

**为什么从「建表」开始，不从 Controller 开始？**
数据是地基。没想清楚「数据长什么样、存哪」就写接口，必然返工。

## 四、两个心法（把 Java / Spring / MyBatis 串起来）

### 心法一：Spring 是「装配车间」（IOC 容器）

你以前自己 `new` 对象、自己连线；Spring 把这两件事全包了。

```java
@Service
@RequiredArgsConstructor              // Lombok 自动生成构造器
public class XxxService {
    private final XxxMapper xxxMapper;   // ← 声明"我要一个 XxxMapper"
    private final RedisTemplate rt;      // ← 声明"我要一个 Redis 操作器"
}
```

- `@Service/@Controller/@Repository` = 告诉 Spring「把我造出来」；
- `private final xxx` = 告诉 Spring「我需要 xxx 塞给我」，这就是**依赖注入**。

**一句话**：你只写「谁依赖谁」，`new` + 连线的事 Spring 包了。

### 心法二：请求走「流水线」（分层架构）

```
浏览器/测试
   │  GET /api/user/1
   ▼
Controller 层 —— 收请求、解析参数，不写业务
   │ 调用
   ▼
Service 层 —— 写业务逻辑（核心）
   │ 调用                │ 调用
   ▼                    ▼
Mapper 层 —— 查 MySQL   RedisTemplate —— 查缓存
   ▼                    ▼
MySQL 表 t_user        Redis
```

**为什么要分层**：每层只干一件事，坏了哪层换哪层。
对照你熟悉的 MyBatis：Controller=`@RestController`、Service=`@Service`、Mapper=`UserMapper`+XML，本来就是这条流水线。

## 五、Service 万能模板（缓存套路，背下来）

任何「查数据 + 加缓存」的功能，Service 都是这个骨架：

```java
public Xxx getXxx(Long id) {
    // 1. 拼 key
    String key = "xxx:info:" + id;

    // 2. 查缓存，命中直接返回
    String json = redis.opsForValue().get(key);          // GET xxx:info:1
    if (json != null) return JSON.parseObject(json, Xxx.class);

    // 3. 未命中，查数据库
    Xxx data = xxxMapper.selectById(id);                  // SELECT ...
    if (data == null) throw new RuntimeException("不存在");

    // 4. 写缓存（带过期）+ 返回
    redis.opsForValue().set(key, JSON.toJSONString(data), Duration.ofMinutes(30)); // SET ... EX 1800
    return data;
}

public Xxx updateXxx(Long id, ...) {
    // 1. 先改数据库
    // 2. 再删缓存 redis.delete(key)                        // DEL xxx:info:1
    // 3. 返回
}
```

剩下的案例，只是把这个模板里的「数据类型」和「操作」换一换：
- 商品 → `opsForHash`（字段级更新）
- 点赞 → `opsForSet`（判断谁点过赞）
- 排行 → `opsForZSet`（排序）

## 六、记忆锚点（合上屏幕只记这 4 句）

1. **Spring 是装配车间**：你声明依赖（`private final`），它负责 new + 连线。
2. **请求走流水线**：Controller（收）→ Service（逻辑）→ Mapper（查库）＋ RedisTemplate（查缓存）。
3. **施工从表往上搭**：建表→实体→Mapper→Service→Controller，每层独立验证。
4. **看懂四问**：哪种结构 / 什么 key / TTL 多久 / 为什么用这个结构。
