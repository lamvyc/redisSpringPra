# 案例1 · 用户信息缓存（String + Cache Aside）

> 技术方案：String 存用户对象 + Cache Aside（旁路缓存）
> 学什么：**最基础的缓存套路**（先查缓存→查库→写缓存；改库→删缓存），后面 9 个案例都在这基础上变。
>

# Part A · 看懂版

## A1. 全景流程图（这个案例到底在干嘛）

```
浏览器/测试
    │  GET /api/user/1
    ▼
UserCacheController        ← 接口入口，不写业务，只转发
    │
    ▼
UserCacheService.getUserById(1)   ← 核心，逐行读这里
    │
    ├─ ① 查缓存 ──→ redisTemplate.opsForValue().get("user:info:1")  =  GET user:info:1
    │       │ 命中 → 直接返回（不打数据库，快）
    │       └ 未命中 ↓
    ├─ ② 查 MySQL ──→ userRepository.findById(1)                    =  SELECT * FROM t_user WHERE id=1
    │
    └─ ③ 写回缓存 ──→ redisTemplate.opsForValue().set(key,user,30min)= SET user:info:1 {...} EX 1800
```

一句话：**先看缓存有没有 → 没有就查库 → 拿到后顺手放缓存 → 下次直接命中。**

这就是 **Cache Aside（旁路缓存）**，面试反复问。

## A2. 两个「武器」（不搞懂这俩后面全懵）

```java
private final RedisTemplate<String, Object> redisTemplate;  // 操作 Redis
private final UserRepository userRepository;                // 操作 MySQL
```

- **RedisTemplate<String, Object>**：key 是字符串，value 存 **User 对象**。为什么用 `RedisTemplate` 不用 `StringRedisTemplate`？因为 value 要存对象，需要「序列化成 JSON 存进去、反序列化回 User 读出来」。这套转换在 `RedisConfig.java` 里配好了，你只需知道：**塞 User 进去，读出来能 `(User)` 强转回来**。
- **UserRepository**：对标你的 MyBatis-Plus，别被 JPA 吓到：

| 本项目 JPA        | 你熟悉的 MyBatis-Plus     |
|----------------|-----------------------|
| `findById(id)` | `selectById(id)`      |
| `save(user)`   | `insert / updateById` |

## A3. 逐行翻译：`getUserById`（读路径，核心）

```java
String key = RedisKeyConstants.USER_INFO + userId;
// → key = "user:info:" + 1 = "user:info:1"

Object cached = redisTemplate.opsForValue().get(key);
// → GET user:info:1
//   opsForValue() = 操作 String 类型；.get() = GET

if (cached != null) {
    return (User) cached;   // 命中，直接返回，不打数据库
}
// 为什么能强转？当初存进去的就是 User，RedisConfig 的 JSON 序列化读出来自动还原

User user = userRepository.findById(userId)
        .orElseThrow(() -> new BizException("用户不存在"));
// → SELECT * FROM t_user WHERE id = 1；查不到抛「用户不存在」

redisTemplate.opsForValue().set(key, user, CACHE_TTL);  // CACHE_TTL = 30 分钟
// → SET user:info:1 {"id":1,...} EX 1800
// 为什么设 30 分钟 TTL？不设会永远留在 Redis，数据库改了也读不到新数据。
// TTL 就是「缓存数据的保鲜期」，到期自动失效、下次重新查库。
```

## A4. 逐行翻译：`updateUser`（写路径，最常被问「为什么」）

```java
userRepository.save(user);        // ① 先改 MySQL：UPDATE t_user SET ... WHERE id=1
redisTemplate.delete(key);        // ② 再删缓存：DEL user:info:1
```

### ⭐ 为什么「删缓存」而不是「更新缓存」？

| 方案 | 做法 | 问题 |
|------|------|------|
| ❌ 更新缓存 | DB 改完 → 把新 User 写进缓存 | 并发时后写覆盖先写，容易不一致，还容易写错 |
| ✅ 删除缓存 | DB 改完 → 直接删缓存 | 简单不会错，下次读时自动去 DB 拿最新重建 |

核心思想 = **延迟加载**：缓存不主动维护，删掉它，让下次查询被动重建最新值。越简单越不容易错。

**为什么要「先 DB 后删缓存」？** 反过来「先删缓存再改 DB」，删和改之间有空档，大量请求发现缓存没了全涌去数据库（缓存击穿风险）。先 DB 后删缓存，空档最小。

## A5. 辅助方法

```java
redisTemplate.delete(key);                          // DEL user:info:1
redisTemplate.getExpire(key, TimeUnit.SECONDS);     // TTL user:info:1（查剩余秒数）
// 注意：getExpire = TTL，方法名里没有"TTL"三个字母，最容易懵的一个
```

## A6. 测试剧本（验证闭环）

```java
getUserById(1L)      // ① 首次：缓存无 → 查库 → 写缓存
getUserById(1L)      // ② 再次：缓存命中，不再查库
updateUser(1L,...)   // ③ 改 DB → 删缓存
getUserById(1L)      // ④ 再查：缓存已删 → 重新查库 → 拿到新名字
```
这段测试就是整个案例的「剧本」：证明「第一次走库、第二次走缓存、更新后缓存被删、再查拿到新值」。

# Part B · 从0实现版

> 目标：关掉项目代码，从空文件夹自己写出来。

## B1. 需求（一句话）

> 输入用户 id，输出用户信息；先查 Redis，命中直接返回；没命中查 MySQL 并写进 Redis，30 分钟过期。

## B2. 建表 + 实体

```sql
CREATE TABLE t_user (
    id   BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    age  INT
);
```

```java
@Data
public class User {            // 一个对象对应表里一行
    private Long id;
    private String name;
    private Integer age;
}
```

## B3. Mapper（你熟悉的 MyBatis-Plus）

```java
// 继承 BaseMapper 即获得 selectById / updateById
public interface UserMapper extends BaseMapper<User> { }
```

## B4. Service（核心：先「内心独白」再翻译成代码）

**内心独白**：
> 我要查用户，数据在 MySQL。但每次都查库慢，所以加一层 Redis。
> 读 = 先问 Redis 有没有 → 有直接返回（快）→ 没有查 MySQL → 查到顺手存 Redis（下次就快）。
> 写 = 改 MySQL → 删 Redis（让下次读重新拿最新）。

翻译成代码：

```java
@Service
@RequiredArgsConstructor
public class UserCacheService {

    private final UserMapper userMapper;          // 操作 MySQL
    private final StringRedisTemplate redis;      // 操作 Redis

    public User getById(Long id) {
        String key = "user:info:" + id;

        // ① 查缓存：GET user:info:1
        String json = redis.opsForValue().get(key);
        if (json != null) {
            return JSON.parseObject(json, User.class);  // 命中：JSON 还原成 User，直接返回
        }

        // ② 未命中，查库
        User user = userMapper.selectById(id);
        if (user == null) throw new RuntimeException("用户不存在");

        // ③ 写缓存：SET user:info:1 {...} EX 1800
        redis.opsForValue().set(key, JSON.toJSONString(user), Duration.ofMinutes(30));
        return user;
    }

    public User update(Long id, String name) {
        // ① 先改 MySQL
        User user = userMapper.selectById(id);
        user.setName(name);
        userMapper.updateById(user);

        // ② 再删 Redis：DEL user:info:1（下次读自动重建最新缓存）
        redis.delete("user:info:" + id);
        return user;
    }
}
```

### ⚠️ 两个手写细节（正好补你缺的那块）

1. **存对象要转 JSON**：`JSON.toJSONString(user)` 存进去、`JSON.parseObject(json, User.class)` 读出来。Redis 只认字符串，不认 Java 对象——这是手写时必须做的翻译。
2. **项目里为什么看不到这两句？** 因为项目的 `RedisConfig` 配了自动序列化，`RedisTemplate<Object>` 帮你偷偷做了这两步。**看懂手写版，再看项目里 `redisTemplate.opsForValue().set(key, user, ttl)` 就知道它只是把翻译藏起来了。**

## B5. Controller（暴露接口）

```java
@RestController
@RequestMapping("/api/user")
@RequiredArgsConstructor
public class UserController {

    private final UserCacheService userCacheService;   // 声明依赖，Spring 自动注入

    @GetMapping("/{id}")                                // GET /api/user/1
    public User get(@PathVariable Long id) {
        return userCacheService.getById(id);            // 只转发，不写业务
    }
}
```

## 记忆锚点（一页纸）

- **读**：`get`=`GET`，命中返回；未命中查库再 `set` 写回（30 分钟 TTL）。
- **写**：先改 DB，再 `delete`（=`DEL`）删缓存，下次读自动重建。
- **TTL**：`set(key,value,Duration)` 设过期；`getExpire` 查剩余（=`TTL`）。
- **为什么删不更新**：延迟加载，简单不易错。
- **面试版**：Cache Aside——读：查缓存→未命中查库→写缓存；写：先更新库→再删缓存。
